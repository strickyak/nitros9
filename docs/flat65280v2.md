# flat65280v2 Hardware & System Specification

This document defines the hardware environment, memory layout, and direct-boot mechanism for the **flat65280v2** emulator running NitrOS-9 Level 1.

> [!NOTE]
> Address ranges in this document use `..` to indicate an **inclusive range** (e.g., `$FF80..$FF86` includes both `$FF80` and `$FF86`).

---

## 1. Memory Map

| Address Range (Inclusive) | Size | Function |
|---|---|---|
| `$0000..$FEFF` | 65,280 bytes (`$FF00`) | **Flat RAM** (OS, kernel, system buffers, free RAM, and user processes) |
| `$FF00..$FFFF` | 256 bytes (`$0100`) | **I/O "Red Page" & System Vectors** |

---

## 2. I/O Devices in "v2"

In the "v2" emulator, three I/O devices are implemented in the top page:

### EMUDSK (`$FF80..$FF86`)
A standard NitrOS-9 virtual block storage device interface:

| Address | Register | Description |
|---|---|---|
| `$FF80` | `LSN[23:16]` | High byte of 24-bit Logical Sector Number |
| `$FF81` | `LSN[15:8]` | Mid byte of 24-bit Logical Sector Number |
| `$FF82` | `LSN[7:0]` | Low byte of 24-bit Logical Sector Number |
| `$FF83` | `COMMAND` / `STATUS` | Write: `0` = Read Sector, `1` = Write Sector. Read: Status code |
| `$FF84..$FF85` | `BUFFER` | 16-bit RAM buffer pointer (big-endian) |
| `$FF86` | `DRIVE` | Drive unit selection (`0` = Drive 0, `1` = Drive 1) |

### CLOCK_AND_STOP (`$FF87`)
A programmable periodic interrupting clock and immediate emulator execution/lifecycle control port:

| Address | Register | Description |
|---|---|---|
| `$FF87` | `CLOCK_AND_STOP` | Periodic tick interrupt control, frequency selection, and abrupt emulator stop commands. |

#### Register Bit Layout (`$FF87`)

| Bit(s) | Mask | Name | Access | Function / Description |
|:---|:---|:---|:---|:---|
| **0** | `$01` | `TICK` | R / W1C | **Firing Condition / Clock Tick Flag**:<br>• **Read**: `1` = Clock has ticked / interrupt pending; `0` = Cleared / idle.<br>• **Write**: Writing a byte with bit 0 set to `1` resets this flag to `0`. Writing a byte with bit 0 as `0` leaves this flag unaltered. Cannot be set to `1` by user writes. |
| **1** | `$02` | `IRQ_EN` | R/W | **IRQ Enable**: `1` = Asserts CPU `IRQ` line whenever bit 0 (`TICK`) is `1`; `0` = Masks/disables hardware IRQ generation from the clock. |
| **2..3** | `$0C` | `USER[1:0]` | R/W | General-purpose read/write bits; preserved as written by the user. |
| **4..5** | `$30` | `RATE[1:0]` | R/W | **Clock Frequency Select** (Bits `$30`):<br>• `$00` (`%00000000`): **60 Hz** (default, ~33,333 cycles at 2 MHz)<br>• `$10` (`%00010000`): **50 Hz** (~40,000 cycles at 2 MHz)<br>• `$20` (`%00100000`): **6 Hz** (~333,333 cycles at 2 MHz)<br>• `$30` (`%00110000`): **0.1 Hz** (1 tick every 10 seconds, ~20,000,000 cycles at 2 MHz) |
| **6..7** | `$C0` | `USER[3:2]` | R/W | General-purpose read/write bits; preserved as written by the user. |

#### Operational Characteristics & Rules

1. **Periodic Tick Event**:
   - Each time the configured timer interval elapses, hardware sets bit 0 (`ClockAndStop |= 0x01`).
   - If bit 1 (`IRQ_EN`) is enabled, the CPU `IRQ` line is asserted (`clockIRQ = (ClockAndStop & 0x01 != 0) && (ClockAndStop & 0x02 != 0)`).
2. **Interrupt Acknowledgment (Write-1-to-Clear / W1C)**:
   - Writing a byte with bit 0 set to `1` resets the tick flag to `0` (and deasserts `IRQ`).
   - Writing a byte with bit 0 set to `0` leaves the tick flag unaltered.
   - User writes cannot force bit 0 to `1`; only periodic hardware timer ticks can set bit 0.
3. **Read/Write User Bits**:
   - All bits besides bit 0 (bits 7..1) are standard read/write bits, only set by user writes. Reading `$FF87` returns the current tick flag in bit 0 and the exact user-written values in bits 7..1.
4. **Abrupt Emulator Stop Commands**:
   - Writing specific values to `$FF87` causes the emulator to stop abruptly. Before halting, the emulator flushes output and prints an explanatory message to `stdout` and `stderr`:
     - **`$FC`**: Prints `\n *** Exiting with status 0 due to CLOCK_AND_STOP command $FC.\n` and exits with host status code 0 (`exit(0);`).
     - **`$FD`**: Prints `\n *** Exiting with status 1 due to CLOCK_AND_STOP command $FD.\n` and exits with host status code 1 (`exit(1);`).
     - **`$FE`**: Prints `\n *** Crashing due to CLOCK_AND_STOP command $FE.\n` and induces an immediate crash / core dump (via `SIGABRT` / panic).

### ACIA_M6805 (`$FF88..$FF89`)
Motorola ACIA serial interface for terminal console communication:

| Address | Register | Description |
|---|---|---|
| `$FF88` | `STATUS` / `CONTROL` | **Read**: ACIA Status Register (Rx ready, Tx empty, IRQ flags).<br>**Write**: ACIA Control Register (reset, baud/clock divide, parity/word format). |
| `$FF89` | `DATA` | **Read**: Rx Data Register (read received byte).<br>**Write**: Tx Data Register (transmit byte). |

|---|---|

| `$FFF2..$FFF3` | SWI3 |

| `$FFFE..$FFFF` | **RESET** (points directly to `OS9Cold` entry in `krn`) |

## 4. NitrOS-9 Level 1 RAM Layout

In this environment, RAM is a single flat address space (`$0000..$FEFF`) with no artificial partition or defined notion of "high" vs "low" RAM. Preloaded system modules are positioned up against the `$FF00` "Red Page" boundary (the highest module byte sitting at `$FEFF`):

```text
$0000 +------------------------------------------+
      | System Globals ($0020..$0111)            |
$0200 +------------------------------------------+
      | Free Memory Bitmap & Dispatch Tables     |
$0300 +------------------------------------------+
      | Module Directory ($0300..$03FF, 64 slots)|
$0400 +------------------------------------------+
      | System Stack ($0400..$04FF)              |
$0500 +------------------------------------------+
      | Free RAM Pool                            |
      | (Zeroed bytes available for user procs)  |
      | ...                                      |
BtLO  +------------------------------------------+
      | Preloaded NitrOS-9 OS Modules            |
      | (krn, krnp2, ioman, rbf, scf, init,      |
      |  drivers, descriptors, sysgo, shell)     |
$FEFF +------------------------------------------+
$FF00 | "Red Page" (Hardware I/O & Vectors)      |
$FFFF +------------------------------------------+
```

1. **Module Placement**:
   - System modules are packed contiguously, terminating immediately before the `$FF00` "Red Page" boundary at `$FEFF`.
2. **Pre-Zeroed Memory**:
   - All unused memory below the preloaded modules down to `$0000` is initialized to zero bytes before startup.
   - `$0000..$04FF` is claimed by the kernel during initialization for system variables, dispatch tables, module directory entries, and the initial system stack.
   - Memory between `$0500` and the bottom of the preloaded modules forms the initial free RAM pool for user processes and system allocations.

## 5. Direct Preloaded Kernel Boot Mechanism

While the general module placement against `$FF00` is standard, the booting mechanism is **atypical**:

### No Multi-Stage Boot Required
Traditional NitrOS-9 systems boot in multiple stages (ROM bootstrap -> hardware boot driver -> reading `OS9Boot` from floppy/disk -> linking modules into RAM). The **flat65280v2** emulator eliminates this entire pipeline:
- **No boot devices** (no floppy controller, WD1773, or initial disk read needed to boot).
- **No boot drivers** (no `boot_emu`, `boot_sdc`, or ROM loaders).
- **No prelude hack**: The deprecated `level1prelude.asm` stub and its pointer/magic-number table at `$FEF8..$FEFF` are discarded.

### How Direct Boot Works
1. **Magic Preload**:
   - Prior to CPU reset, the emulator loads the compiled OS modules directly into RAM ending at `$FEFF`, with all memory below zeroed out.
2. **Reset Vector Target**:
   - The emulator populates the CPU RESET vector at `$FFFE..$FFFF` with the exact execution entry address of the main kernel module (`krn`), which is computed from the kernel's OS-9 module header (`ModTop` + execution offset `M$Exec` pointing to `OS9Cold`).
3. **Hardware Reset Sequence**:
   - When the 6809 CPU starts or resets, it fetches the reset vector from `$FFFE..$FFFF` and begins execution directly at `OS9Cold` in `krn`.
4. **Kernel Self-Initialization**:
   - The kernel masks interrupts (`orcc #$50`) and sets the system stack pointer to `$0500`.
   - The kernel sets up system tables and **scans all of RAM** (up to the `$FF00` "Red Page" boundary) looking for modules. Rather than calling validation subroutines on every byte, it scans rapidly (pre-checking for module sync bytes before invoking full verification) and registers all discovered modules into the Module Directory.
   - The kernel locates `Init` and forks the primary system process (`SysGo`), transitioning directly into multi-user / shell operation.

## 6. Legacy Level1 Boot Annoyances

Historical analysis of the standard Level 1 kernel (`krn.asm`) and bootstrap routines (`rel.asm`) reveals several architectural flaws and inefficiencies that our clean `flat65280v2` environment avoids:

1. **Conditional Compilation Spaghetti**:
   - The main kernel source is overwhelmed by nested, target-specific conditional assembly switches (`IFNE wildbits`, `IFNE atari`, `IFNE corsham`, `IFNE CHECK_FOR_VALID_RAM`, `IFNE dalpha`, etc.). This obscures the fundamental kernel initialization logic and makes the codebase fragile to read and maintain.

2. **Unsafe / Forgotten Stack (`S`) Pointer Reset**:
   - On an M6809 power-on or hardware reset, the `S` register is uninitialized or `$0000`. Any register push (`pshs`), subroutine call (`bsr`), or interrupt occurring before `S` is set causes the stack pointer to pre-decrement to `$FFFE..$FFFF`—writing directly into the I/O "Red Page" or exception vectors. On an emulator with strict fault checking, this triggers an immediate fault and crash. Legacy bootstrap code sometimes neglected to establish a valid `S` immediately before pushing registers.

3. **Redundant Zeroing of Low Memory**:
   - The kernel spends CPU cycles executing an explicit loop (`loop@ std ,x++`, `leay -2,y`) clearing `$0000..$0400`. In modern emulator or preloaded setups, the host environment already guarantees that memory below the modules is initialized to zero.

4. **Inefficient Module Scanning (`ValMods`)**:
   - In standard Level 1 `ValMods`, the kernel scans through memory by calling `lbsr ValMod` on **every single byte address** without first checking for the standard 2-byte OS-9 module sync header (`$87CD`).
   - Every non-module byte incurs the heavy overhead of a full subroutine call, stack frame creation, parameter setup, parity verification, and error return. Over kilobytes of empty RAM, this wastes tens of thousands of subroutine calls.

5. **Hardcoded Module Search Start Addresses**:
   - The start of the module search range is often hardcoded to a fixed equate (e.g., `Bt.Start`, typically `#$2600` or `#$8000`). If preloaded modules in a flat RAM system are placed lower in memory than this hardcoded threshold, the kernel will fail to discover, validate, or register them into the Module Directory.

6. **Destructive Screen Memory Scribbling around `$8000`**:
   - Legacy CoCo boot code (such as in `rel.asm`) assumes standard Color Computer VDG hardware. During initialization, it points SAM video registers to `$8000` and clears 512 bytes with green blank characters (`sta ,x+` with `$60` into `$8000..$81FF`). In an embedded or virtual system where preloaded OS-9 modules may reside at or span across `$8000`, this blindly corrupts module code and data.

7. **Rigid Size and Location Constraints**:
   - Legacy bootstrap code and build scripts frequently enforce strict size limits (e.g., forcing modules to be padded to fixed byte boundaries such as 1024 or 4608 bytes via `padrom`) and require rigid physical memory placements for specific modules. This severely defeats the core OS-9 philosophy of flexible, position-independent, relocatable modules that can be sized naturally and loaded anywhere in available memory.

## 7. Proposed Kernel Startup & Optimized Module Scanning (`krn.asm`)

> [!NOTE]
> This section documents our tentative startup sequence and module-scanning algorithm. It is subject to adjustment as implementation proceeds.

### Kernel Startup Sequence

1. **Immediate Stack & Mask**:
   - Establish `S = $0500` and mask interrupts (`orcc #$50`) as the very first instruction of `OS9Cold`.
2. **Omit Redundant Zeroing**:
   - Skip clearing `$0000..$0400` in software; the emulator guarantees that all RAM below preloaded modules is zeroed.
3. **Set Up System Globals Area**:
   - Initialize system pointers:
     - `D.FMBM = $0200` (Free memory bitmap start, 32 bytes)
     - `D.FMBM+2 = $0220` (Free memory bitmap end)
     - `D.SysDis = $0222` (System dispatch table)
     - `D.UsrDis = $0292` (User dispatch table)
     - `D.ModDir = $0300` (Module directory start, ending at `$0400`)
4. **Omit `CHECK_FOR_VALID_RAM`**:
   - Memory is flat, contiguous RAM up to `$FEFF`. `D.MLIM` is set directly to `$FEFF`.
5. **Copy Vectors to System Globals**:
   - Copy the vector trampoline stubs to `D.XSWI3` (`$0100`).
6. **Fill In More System Globals**:
   - Populate `D.URtoSs`, `D.UsrIRQ`, `D.UsrSvc`, `D.SysIRQ`, `D.SvcIRQ`, `D.SysSvc`, `D.SWI2`, `D.NMI`, `D.Poll`, `D.Clock`, and `D.AltIRQ` with internal kernel handlers.
7. **Install System Calls**:
   - Call `InstallSvc` with `SysTbl`.
8. **Set Up Free Memory Bitmap**:
   - Mark pages `$00..$04` (`$0000..$04FF`) as allocated in `D.FMBM`.

---

### Optimized In-Memory Module Scanning Algorithm (`ValMods`)

Rather than scanning byte-by-byte with subroutine calls across all memory, the new `ValMods` algorithm leverages the pre-zeroed RAM and standard OS-9 module headers (`$87CD`):

```text
               +-------------------------------------------+
               | Start at $0800                            |
               +-------------------------------------------+
                                     |
                                     v
               +-------------------------------------------+
Phase 1        | Fast Stride-2 Pre-Scan:                   |
(Zeroed RAM)   | Advance by 2 bytes while data is zero     |
               +-------------------------------------------+
                                     |  Hits non-zero ($87 or $CD)
                                     v
               +-------------------------------------------+
Phase 2        | Back up 1 byte (leax -1,x).               |
(Header Sync)  | Scan byte-by-byte for $87 then $CD        |
               +-------------------------------------------+
                                     |  Sync matched
                                     v
               +-------------------------------------------+
Phase 3        | Call ValMod to verify parity & header.    |
(Registration) | - If valid: advance X by M$Size.          |
               | - If invalid: advance X by 1 byte.        |
               +-------------------------------------------+
                                     |
                                     v
               +-------------------------------------------+
               | Repeat until X reaches $FEF8 boundary     |
               +-------------------------------------------+
```

1. **Phase 1 — Fast Non-Zero Pre-Scan (Stride of 2)**:
   - Begin scanning at `$0800`, safely past the low-RAM system structures.
   - Advance through memory in 2-byte increments (`leax 2,x` or `ldd ,x++`), testing for any non-zero word.
   - Because every OS-9 module begins with a 2-byte sync word (`$87CD`), stepping by 2 across zeroed RAM is guaranteed to hit either the first byte (`$87`) or the second byte (`$CD`) of the first preloaded module header immediately upon encountering non-zero memory.
2. **Phase 2 — Sync Word Alignment**:
   - Upon detecting a non-zero byte, back up by 1 address (`leax -1,x`) to catch the header in case the stride landed on the second sync byte (`$CD`).
   - Run a tight, inline single-byte search comparing against `$87` followed by `$CD`.
   - Non-sync bytes are skipped with zero subroutine call overhead.
3. **Phase 3 — Validation & Stride-by-Size**:
   - Only when the 2-byte sync pattern is confirmed is `lbsr ValMod` called to verify header parity and register the module in `D.ModDir`.
   - On successful validation, `X` advances immediately by the module's total declared size (`ldd M$Size,x; leax d,x`), skipping the entire validated module body.
   - If validation fails, `X` advances by 1 byte and resumes searching.
4. **Search Upper Bound (`$FEF8`)**:
   - Scanning stops at `$FEF8`. Since the minimum valid OS-9 module header requires at least 9 bytes (and full modules include name strings and CRC), no valid module can begin after `$FEF8` before the `$FF00` boundary.

## 8. Conditional Assembly & Port Integration Strategy (`FLAT65280`)

To integrate cleanly into the shared NitrOS-9 repository without breaking existing ports or exacerbating legacy conditional complexity, we adhere to the following principles:

### 1. The `FLAT65280` Symbol
- Our target is selected by defining `FLAT65280 EQU 1` in our port's definitions (`defsfile` / `port.mak`).
- Because NitrOS-9 builds with `lwasm --pragma=condundefzero`, the symbol `FLAT65280` automatically evaluates to `0` across all other ports (`coco1`, `coco3`, `wildbits`, `atari`, `corsham`, etc.) without requiring edits to their port configuration files.

### 2. Coarse-Grained Replacement Over Micro-Conditionals
- Rather than inserting fine-grained `IFNE FLAT65280` switches inside already tangled, multi-level conditional ladders, we isolate whole functional blocks:
  - **Shared Universal Logic (Zero Conditionals)**: Common kernel infrastructure (setting globals, copying vector stubs to `$0100`, installing system call tables, linking `Init`, and jumping to `krnp2`) remains 100% shared without unnecessary conditional wrappers.
  - **RAM Sizing Block**: The 60-line legacy `CHECK_FOR_VALID_RAM` / port cascade is enclosed in `ELSE`, while the `IFNE FLAT65280` branch directly sets `D.MLIM = $FEFF`.
  - **Module Search Range Setup**: The legacy `atari / corsham / wildbits / Bt.Start` cascade is enclosed in `ELSE`, while `IFNE FLAT65280` simply loads `X = $0800`, `Y = $FEF8`, and calls `ValMods`.
  - **`ValMods` Implementation**: Our optimized 3-phase scanning algorithm is placed under `IFNE FLAT65280`, while the legacy byte-by-byte scan is preserved in the `ELSE` branch.

### 3. Repository Citizenship & Backward Compatibility
- Legacy targets retain their exact, unmodified code paths in `ELSE` blocks, ensuring bit-for-bit identical binary builds for all existing systems.
- Our code paths remain concise, legible, and self-contained, avoiding further entanglement of the shared kernel source.

## 9. Emulator Fault & Protection Rules

To catch stray memory accesses and uninitialized device probes:

- **Stray Reads**: Any stray read in `$FF01..$FFEE` (outside the valid I/O registers `$FF80..$FF86`, `$FF87`, and `$FF88..$FF89`) will trigger a **Fault** and cause the emulator to stop.
- **Stray Writes**: Any stray write anywhere in the top page `$FF00..$FFFF` (outside the designated write registers of EMUDSK, CLOCK_AND_STOP, and ACIA_M6805) will trigger a **Fault** and cause the emulator to stop.

## 13. Subsystem Bug Fixes & Diagnostics

During emulator bringup, several latent bugs across Level 1 kernel and manager routines were isolated and resolved:

### 1. `level1/modules/ioman.asm` (`AllcPDsc`)
- **Bug**: `AllcPDsc` called `F$All64` to allocate a 64-byte path descriptor block, but neglected to store the returned block number (`A`) into `PD.PD,y` (offset 0).
- **Consequence**: When I/O routines called `S2UPath` to validate user paths, `PD.PD` contained `$00`, causing path lookups to fail with `E$BPNum` ("Bad Path Number").
- **Fix**: Added `sta PD.PD,y` immediately after `F$All64` returns successfully.

### 2. `level1/modules/kernel/fchain.asm` (`SFChain` & `SetupPrc`)
- **Bug 1 (`SFChain`)**: When system code (such as `krnp2`) executed `os9 F$Chain` to launch the initial user program (`Shell`), `SFChain` called `DoChain` but jumped directly to `resched@` without clearing `SysState` in `P$State,x`.
- **Consequence**: `Shell` inherited system state and routed its standard I/O calls through `SysIODis` rather than user `UsrIODis`, bypassing user path resolution.
- **Fix**: Unified `SFChain` into `FChain` so that `andb #^SysState; stb P$State,x` is always executed prior to rescheduling.
- **Bug 2 (`SetupPrc`)**: In `SetupPrc`, successful register and parameter initialization fell through into `badfork@` (`ldb #E$IForkP`) due to a missing unconditional branch.
- **Fix**: Added `bra ex@` before `badfork@`.

### 3. `level1/modules/kernel/krn.asm` (Module Space in `D.FMBM`)
- **Bug**: In Level 1 unpaged memory, `F$Mem` checks `D.FMBM` for free pages. If preloaded modules (`$0800..$A45E`) are left unallocated in the bitmap, `F$Mem` allocates `$0500..$08FF` to child processes, overwriting the kernel code itself.
- **Fix**: Added `stx <D.BTHI` in `ValPhase3` to record the highest validated module address. During bitmap initialization, `krn` calls `AllocBit` to mark pages `0` through `(D.BTHI + $FF) / 256` as allocated, ensuring child allocations start in clean RAM above all modules (`$A500`).

### 4. `level1/modules/kernel/krnp2.asm` (Initial Process Data Address)
- **Bug**: Legacy `krnp2.asm` initialized process 1's `P$ADDR` to `page 4` (the boot stack page) with `P$PagCnt = 1`. In `fmem.asm`, any memory expansion on a process with `P$ADDR != 0` strictly requires that newly allocated free pages be immediately contiguous with `P$ADDR + P$PagCnt`. Because page 5 and higher are occupied by preloaded modules, `F$Chain` into `Shell` failed with `E$MemFul`.
- **Fix**: Under `IFNE FLAT65280`, initialized process 1's `P$ADDR` and `P$PagCnt` to `0`. When `P$ADDR` is zero, `F$Mem` is free to allocate user data space from the free RAM pool above all preloaded modules.
